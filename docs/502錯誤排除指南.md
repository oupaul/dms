# 502 Bad Gateway 錯誤排除指南

## 錯誤說明

**502 Bad Gateway** 錯誤表示：
- 反向代理（如 Nginx）無法連接到後端應用程式
- 應用程式未運行或已崩潰
- 應用程式監聽的端口不正確
- 應用程式啟動時發生錯誤

**常見原因：佈署時 PORT 輸入錯誤**  
若佈署時自訂了服務 Port（例如 8883），請確認：
- 實際連線網址使用正確的 port（如 `http://主機:8883/`）
- Nginx 或反向代理的 `proxy_pass` 指到同一 port
- 檢查監聽時使用**實際佈署的 port**（見下方「步驟 3」）

## 快速診斷步驟

### 方法一：使用自動診斷腳本（推薦）

```bash
# 執行故障排除腳本（自動檢測應用程式）
chmod +x fix_502_error.sh
./fix_502_error.sh

# 指定應用程式名稱（如果自動檢測失敗）
./fix_502_error.sh <應用程式名稱>

# 通過環境變數指定
APP_NAME=<應用程式名稱> ./fix_502_error.sh
```

**注意：** 腳本會自動從以下來源檢測應用程式：
1. PM2 中運行的應用程式（優先，並會自動獲取實際路徑）
2. `/opt` 目錄下的應用程式目錄
3. 如果無法自動檢測，會提示使用預設值或手動指定

腳本會自動：
1. 檢查 PM2 服務狀態
2. 查看應用程式日誌
3. 檢查端口配置和監聽狀態
4. 測試 HTTP 連接
5. 檢查 Nginx 配置（如果使用）
6. 檢查應用程式依賴
7. 嘗試自動修復

### 方法二：手動診斷

#### 步驟 1: 檢查服務狀態

```bash
# 查看 PM2 服務狀態
pm2 status

# 查看特定應用程式狀態
pm2 describe folder-permission-system
```

**可能的狀態：**
- ✅ **online** - 服務正常運行
- ⚠️ **stopped** - 服務已停止
- ❌ **errored** - 服務發生錯誤
- ⚠️ **restarting** - 服務正在重啟

#### 步驟 2: 查看錯誤日誌

```bash
# 查看最近的錯誤日誌（最後 50 行）
pm2 logs folder-permission-system --err --lines 50

# 查看所有日誌
pm2 logs folder-permission-system --lines 50
```

**常見錯誤：**
- 端口已被占用
- 缺少依賴套件
- 資料庫連接錯誤
- 檔案權限問題

#### 步驟 3: 檢查端口監聽

```bash
# 檢查配置的端口（若佈署時自訂為 8883，請改為 8883）
# 預設為 5000，自訂 port 請依佈署時輸入為準
ss -tln | grep :5000
# 或（自訂 port 範例）
ss -tln | grep :8883

# 檢查端口是否被占用
lsof -i :5000
```

#### 步驟 4: 測試本地連接

```bash
# 測試應用程式是否可訪問（port 請改為實際佈署的 port，例如 8883）
curl http://localhost:5000

# 測試 API
curl http://localhost:5000/api/auth/has-accounts
```

## 常見問題和解決方法

### 問題 1: 服務未運行

**症狀：** `pm2 status` 顯示 `stopped` 或應用程式不存在

**解決方法：**

```bash
# 啟動服務
cd /opt/folder-permission-system
pm2 start app.js --name folder-permission-system

# 或使用 ecosystem 配置
pm2 start ecosystem.config.js

# 保存配置
pm2 save
```

### 問題 2: 服務崩潰（errored）

**症狀：** `pm2 status` 顯示 `errored`

**解決方法：**

```bash
# 1. 查看錯誤日誌
pm2 logs folder-permission-system --err --lines 50

# 2. 根據錯誤訊息修復問題（見下方常見錯誤）

# 3. 重啟服務
pm2 restart folder-permission-system
```

### 問題 3: 佈署時 PORT 輸入錯誤（導致 502）

**症狀：** 服務已啟動、日誌無錯誤，但瀏覽器開啟登入頁出現 502

**原因：** 佈署時自訂了服務 Port（例如 8883），但連線時使用了錯誤的 port（如 5000），或 Nginx/反向代理仍指向錯誤的 port。

**解決方法：**

1. 確認佈署時輸入的 Port：查看伺服器上 `app.js` 第一段中的 `const PORT = ?`，即為實際監聽 port。
2. 使用正確網址連線：`http://主機:實際PORT/`（例如 `http://主機:8883/`）。
3. 若使用 Nginx：確認 `proxy_pass` 指向 `http://127.0.0.1:實際PORT;`。
4. 驗證監聽：`ss -tln | grep :實際PORT` 應能看到 node 在監聽。

### 問題 4: 端口已被占用

**症狀：** 日誌顯示 "EADDRINUSE" 或端口無法監聽

**解決方法：**

```bash
# 1. 找出占用端口的進程
lsof -i :5000
# 或
netstat -tlnp | grep :5000

# 2. 停止占用端口的進程
kill -9 <PID>

# 3. 重啟應用程式
pm2 restart folder-permission-system
```

### 問題 5: 缺少依賴套件

**症狀：** 日誌顯示 "Cannot find module" 或 "Module not found"

**解決方法：**

```bash
# 進入應用程式目錄
cd /opt/folder-permission-system

# 重新安裝依賴
npm install

# 檢查關鍵依賴
npm list express sqlite3 exceljs argon2

# 如果缺少，手動安裝
npm install express sqlite3 exceljs argon2
```

### 問題 6: 資料庫錯誤

**症狀：** 日誌顯示資料庫相關錯誤

**解決方法：**

```bash
# 檢查資料庫目錄權限
ls -la /opt/folder-permission-system/databases/

# 修復權限
chmod 775 /opt/folder-permission-system/databases/
chown -R $USER:$USER /opt/folder-permission-system/databases/
```

### 問題 9: 切換資料庫後伺服器崩潰（uncaughtException: SQLITE_ERROR）

**症狀：**
- 切換資料庫成功（顯示「已切換到資料庫」），但緊接著的所有請求都返回 502
- `journalctl` 或 PM2 日誌中出現類似：

```
[uncaughtException] [Error: SQLITE_ERROR: no such column: ms_email] {
  errno: 1,
  code: 'SQLITE_ERROR'
}
systemd: dms-prod.service: Main process exited, code=exited, status=1/FAILURE
```

**根本原因：**

`initializeTables()` 中的 PRAGMA 回調（用於自動補齊舊資料庫缺少的欄位）在 node-sqlite3 **parallel 模式**下執行時，`ALTER TABLE ... ADD COLUMN ms_email` 與 `CREATE UNIQUE INDEX ... ON accounts(ms_email)` 兩條語句可能發生競爭：

1. CREATE INDEX 搶在 ALTER TABLE 完成前執行
2. ms_email 欄位不存在 → `SQLITE_ERROR: no such column: ms_email`
3. 兩條語句都沒有錯誤回調（no callback）→ node-sqlite3 對 database 物件 emit `error` 事件
4. 沒有 `error` 監聽器 → Node.js 升級為 `uncaughtException`
5. `process.on('uncaughtException')` 呼叫 `process.exit(1)` → 伺服器崩潰

**修復方式（已在 v2.x+ 實現）：**

```javascript
// 修復前（有競爭風險）
database.run("ALTER TABLE accounts ADD COLUMN ms_email TEXT");
database.run("CREATE UNIQUE INDEX IF NOT EXISTS idx_accounts_ms_email ...");

// 修復後（用 serialize 保證順序 + 加錯誤回調）
database.serialize(() => {
  database.run("ALTER TABLE accounts ADD COLUMN ms_email TEXT",
    (e) => { if (e) console.warn('migrate accounts.ms_email:', e.message); });
  database.run("CREATE UNIQUE INDEX IF NOT EXISTS idx_accounts_ms_email ...",
    (e) => { if (e) console.warn('migrate idx_accounts_ms_email:', e.message); });
});
```

**受影響的資料庫：** 在 `ms_email` 欄位加入前建立的舊版資料庫（`accounts` 表缺少 `ms_email` 欄位）。首次連線時觸發自動遷移，遷移完成後即不再發生。

**臨時緩解（若無法立刻更新程式碼）：**

```bash
# 手動為受影響的資料庫加入 ms_email 欄位，消除自動遷移觸發條件
sqlite3 /opt/dms-prod/databases/<affected>.db \
  "ALTER TABLE accounts ADD COLUMN ms_email TEXT;"
sqlite3 /opt/dms-prod/databases/<affected>.db \
  "CREATE UNIQUE INDEX IF NOT EXISTS idx_accounts_ms_email ON accounts(ms_email) WHERE ms_email IS NOT NULL;"
```

執行後重啟服務即可。

### 問題 7: Nginx 配置錯誤

**症狀：** 使用 Nginx 反向代理時出現 502

**解決方法：**

```bash
# 1. 檢查 Nginx 配置
sudo nginx -t

# 2. 檢查 Nginx 錯誤日誌
sudo tail -f /var/log/nginx/error.log

# 3. 檢查反向代理配置
sudo grep -r "proxy_pass" /etc/nginx/

# 4. 確保 Nginx 配置指向正確的端口
# 例如：proxy_pass http://localhost:5000;
```

### 問題 8: 應用程式啟動緩慢

**症狀：** 應用程式需要很長時間才能啟動

**解決方法：**

```bash
# 增加 PM2 啟動超時時間
pm2 restart folder-permission-system --update-env

# 或修改 ecosystem.config.js 增加啟動延遲
```

## 手動測試應用程式

如果 PM2 無法啟動，可以手動測試：

```bash
# 進入應用程式目錄
cd /opt/folder-permission-system

# 直接運行應用程式（會顯示詳細錯誤）
node app.js
```

這會顯示啟動時的所有錯誤訊息，幫助定位問題。

## 檢查系統資源

有時 502 錯誤是由於系統資源不足：

```bash
# 檢查磁碟空間
df -h

# 檢查記憶體
free -h

# 檢查 CPU 使用
top
```

如果資源不足，需要：
- 清理磁碟空間
- 增加記憶體
- 關閉不必要的服務

## 完整重啟流程

如果以上方法都無法解決，嘗試完整重啟：

```bash
# 1. 停止服務
pm2 stop folder-permission-system
pm2 delete folder-permission-system

# 2. 檢查並修復依賴
cd /opt/folder-permission-system
npm install

# 3. 檢查配置
grep "const PORT" app.js

# 4. 手動測試
node app.js
# 如果手動測試成功，按 Ctrl+C 停止

# 5. 使用 PM2 重新啟動
pm2 start app.js --name folder-permission-system
pm2 save

# 6. 等待幾秒後檢查狀態
sleep 5
pm2 status
curl http://localhost:5000
```
